# Stage C5 (GTDB R226 complete genomes, Enterobacterales to *Vibrio*) built into the data root (card C-47 part 1)

Date: 2026-11-19 11:00 CST to 2026-11-20 23:03 CST, wilkcomp02 (the pod's clock). Every number carries a label:
*measured* (host, date, command or record), *derived* (formula and inputs) or *estimate*. The card: the stage only,
at depth `annotated`, with Pfam 38.2 scanned **in full** (the plan copying rows earlier stages measured, card B-47b)
and both CRISPR producers; no `--release`, no release step, nothing defined.

**Every stage step of C5 is recorded (48 run records), all seven published releases verify with unchanged manifest
hashes, the corrected check passes, and the stage's 138 files are on `/stor/work` in `added_c5.tar`.** How it got
there, plainly:

1. **Two launches, a day apart.** The first (`c47-c5-1`, 2026-11-19 11:22) published `inputs` and `ingest` and was
   stopped by this card's rate guard at 12:08: ingest cost 45.803 CPU-minutes against the code's estimate of 38.057
   (ratio 1.204, 20.35% over; DEC-53 stops above 1.20). The PI accepted that one record by name and value on
   2026-11-20 (**DEC-56**, "yes, accept c5 ingest and resume"). The second launch (`c47-c5-2`, 2026-11-20 17:18 to
   21:49) resumed at gene calling with the same command.
2. **Stage `V1` was built into the root between them** (card C-48c part 1, 2026-11-20 09:27 to about 16:00): one
   build runs in the root at a time, and `V1` was launched one minute before the PI's answer. C5's resume was queued
   behind it as one detached unit (`c47-queue`), which started when `V1`'s own `after` snapshot was complete.
3. **The `before` listing was taken again after `V1`** (driver mode `rebefore`): the first one (2026-11-19) predates
   `V1`, and the check counts every new file outside `stage=C5` as unexpected. The new listing was taken with the
   seven releases verified, and C5's own 36 already-published files were removed from it, so that `before` means
   "the root without C5": the files added are then all of C5 (its inputs and ingest included) and none of `V1`.
4. **The first check failed on a false positive, and the driver hid it.** `c47_check.py` counted 3 gene-call ledger
   rows `owned_by:C5/<genome_uid>` (a contig listed by two genomes of C5, called once, DEC-27) as earlier-stage skips
   (`2553 != 2550`). The driver then exited 0 (the status of its trailing log line, not of the check), the queue ran
   `backup` on that and wrote "all passed", and an orchestrator waiter started the release train on it at 22:06. The
   check and the driver were fixed test-first (commit `25ac362`); the corrected check, run into a new directory against
   the same snapshots, passes; the backup, made from the first check's `root_added.tsv` (written before its last
   assertion), was not made again: its member list equals the corrected check's list byte for byte.

## 7. The first check, and what was wrong with the check and the driver

- `c47_check.py` (21:51 to 22:02, `check1/report.txt`): every check passed except `genecall ledger earlier skips (2553)
  != stored_by (2550)`. The ledger has 2,653 `ok` rows, 2,550 `owned_by:<earlier stage>` rows (PL1 2,543, P2 3, P4 2,
  P1 1, S1 1) and 3 rows `owned_by:C5/<genome_uid>`. The reason is written as `owned_by:` + `ContigOwners.owner`
  (`src/biobox/l0seq/store.py`): the owning stage, or `<stage>/<genome_uid hex>` for a contig another genome of the
  same stage owns (DEC-27). The check took only the exact `owned_by:C5` as within-stage. The three contigs are stored
  by C5 alone and have genes in C5's `feature_protein`. The stage was right; the check was wrong.
- The driver's `check()` returned the check's status, but the script then ran its trailing `log` line and exited with
  that line's status, 0. The queue judged by the exit status alone, ran `backup` (22:02 to 22:05) and wrote "all
  passed"; that line started the release train for `r26.11.2` at 22:06 (the orchestrator's waiter).
- Fixes (commit `25ac362`, tests first, 15 failing on the pod before the change: `tests/r1/test_c47_check.py`,
  `tests/r1/test_c47_driver.py`): the check classifies a reason by the owner's stage (`skip_kind`), counts within-stage
  skips (`ledger_skipped_within`) and asserts that every stored contig has gene rows or a ledger row; the driver exits
  with the mode's own status; `check` and `backup` refuse without their prerequisites and write `DONE` only on success;
  a later check goes into its own directory (`CHECK_DIR`) and must list the same `root_added.tsv` byte for byte; a
  snapshot fails when a file cannot be hashed; the queue requires each mode's marker, not its exit status alone.
