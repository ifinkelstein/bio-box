## 2. Cause 1: the oom test raced a 3 s wall clock

**Which limit path each environment takes.** The runner picks it in `runstep.memory_cap` and
`runstep.scope_argv`:

| Environment | Cap above the runner | `systemd-run` visible | Path | What holds the worker to 4 GB |
|---|---|---|---|---|
| pod, `scripts/pod_pytest.sh` | 32 GiB (the unit) | no (inside the image) | `inherited`, 4 GB tighter than the cap | `RLIMIT_AS` = 4e9 |
| GitHub `ubuntu-24.04` | none found | yes | `scope` | `MemoryMax=4000000000`, `MemorySwapMax=0` |
| macOS | not read | no | `nice` | nothing (`mem_gb` is None in the test) |

The pod path is *measured*: the failing-first run printed `argv[:4] = ['nice', '-n', '15', python]` and
`mem_cap.memory_max_bytes = 34359738368`. The GitHub path is *derived*, not observed, from three facts:
`systemd-run` is on the image's PATH and no inherited cap was reported, so `memory_cap` returns
"opened"; `[timeout-timeout]` passed in every run, which it could not do if `systemd-run --user
--scope` failed to start the worker (that ends `failed`); and only the scope path can make the `oom`
fault slow. Under `RLIMIT_AS` the fault's `bytearray(8e9)` fails in the allocator at once (the pod
passes every time); with no limit it raises at once.

**What the fault does.** `worker._fault("oom")` allocates `bytearray(2 * limit)`, one allocation that
CPython zero-fills, so it touches every page in order. Under `RLIMIT_AS` that fails before any page is
touched. Under a scope the kernel kills the worker only after it has touched `MemoryMax` of pages, and
the wall clock started when the worker was spawned, so the test needs: worker start-up (imports of
pyarrow, pyhmmer and the search modules) plus touching 4 GB under 3 s.

**How long that takes.** On the pod host, outside the image,
`/usr/bin/time systemd-run --user --scope --quiet -p MemoryMax=4000000000 -p MemorySwapMax=0 nice -n 19 python3 -c 'bytearray(8000000000)'`
was killed by signal 9 after 4.47 s and 5.19 s (two runs); the same scope with `python3 -c pass` took
0.07 s. So the touching alone exceeds 3 s on the pod. In the image the worker reaches the fault about
2.4 s after spawn (*derived*: the A-07 delayed-oom test took 6.37 s with a 4 s injected delay, on the
`RLIMIT_AS` path where the fault itself is instant). GitHub's time is not measured; it failed in
4 of 7 runs, so it sits near 3 s.

**Fix.** The wall clock is the subject of the `timeout` fault only (it sleeps forever, so the wall must
fire, and 3 s keeps that test short). For `oom` and `crash` the wall is not under test, and a wall the
fault can reach makes the outcome depend on the host's page-fault speed. The test's limits are now per
fault (`S05_LIMITS`): `timeout` keeps `wall_s=3`; `oom` and `crash` run under the file's `LIMITS.wall_s`
(120 s), which only a hung worker reaches. The assertions (`status == "oom"`, no hits file) are
unchanged. The fault's work is bounded by construction: `worker.oom_bytes` names twice the limit the
runner gave the worker (`BIOBOX_RLIMIT_AS`, else `BIOBOX_MEMORY_MAX`, the scope's `MemoryMax` or the
inherited cap), it allocates that in one step, and if the allocation succeeds the fault now raises
`RuntimeError(... that limit is not enforced)`, so the run ends `failed`, not `oom`. Before, a scope
whose `MemoryMax` was not enforced still reported `oom` (it touched twice the limit, then raised
`MemoryError("injected")`); the unit test `test_a07_an_oom_fault_that_is_not_stopped_is_failed_not_oom`
showed exit 86 (EXIT_OOM) on the old code.

**Deterministic reproduction.** `test_a07_oom_is_oom_however_long_the_fault_takes_to_reach_its_limit`
sets the worker hook `BIOBOX_OOM_FAULT_DELAY_S=4` (the fault starts 4 s late, as on a host slower to reach
its limit) and runs the oom case under `S05_LIMITS["oom"]`. With the old limits it ended
`('wall-clock timeout', ['nice', '-n', '15', '/opt/bio-box/.venv/bin/python'], ... "wall_s": 3)` on the
pod; with the new limits it ends `oom`.

**Every path has an oom test that does not depend on timing** (`tests/r1/test_search_units.py`):
`test_a07_the_oom_fault_allocates_past_the_limit_that_holds_its_path` (scope, inherited with a
tighter `mem_gb`, inherited cap only, nice, bare, nice on Darwin, scope without `mem_gb`: the fault asks
for twice the limit that holds that path, or names none where none holds);
`test_a07_a_cgroup_kill_of_the_oom_fault_is_oom` (scope and inherited cap: SIGKILL with one more
`oom_kill` than the baseline in `memory.events` is `oom`, without it `failed`);
`test_a07_the_oom_fault_under_rlimit_as_exits_oom_at_once` (nice, bare and inherited-tighter: the real
worker under the real rlimits and environment exits EXIT_OOM); `test_a07_the_oom_fault_without_a_limit_exits_oom`.

## 3. Cause 2: a killed runner's leader is a zombie while its last thread still holds the lock

**Who holds `runner.lock`.** In 20 kills of a real runner on the pod (submit with `fault="timeout"`,
wait for `worker.pid`, SIGKILL the runner, then poll `/proc/<pid>/stat`, `/proc/<pid>/task/*/stat` and a
`LOCK_SH|LOCK_NB` probe in a tight loop), a scan of every `/proc/*/fd` before the kill found exactly one
descriptor on the lock: the runner's fd 5. The worker held none (`systemd-run` and `nice` exec the
worker, and `Popen` closes inherited descriptors). The inherited-fd suspect is ruled out on the pod's
path; `test_a07_only_the_runner_holds_a_descriptor_of_its_lock` now checks it on every Linux run.

**What does.** The runner has 5 threads (`/proc/<pid>/task/*/comm`: `python` ×4 and `jemalloc_bg_thd`).
SIGKILL ends them all, and the thread that exits last tears down the address space and only then
closes the files, which releases the flock. The lock was released 25 to 59 ms after the kill (50
kills, two probe runs). In 2 of the 50 the leader was not the last thread: it showed `Z` 0.9 to 1.1 ms
after the kill, with one other task still `R`, and the lock stayed held until 42.8 to 43.3 ms. A zombie
is what the test's `_alive` (and `ps`) count as gone, so the test then read `status`, the lock probe
found the lock held, and `status` said `running`. When the leader is itself the last thread, it shows
`R` until the lock is free, `_alive` stays true, and the test passes; so the test fails only when
another thread outlives the leader. GitHub's rate (4 of 7 runs, *measured*) is higher than the pod's 2 in 50
(*measured*); why is not established (fewer and busier vCPUs is a guess, an *estimate* at best).

**Fix.** `status` and `cancel` count a runner live only when it holds its lock **and** its process is
alive (`runner_process_alive`): `/proc/<pid>/stat` exists, the state is not `Z` or `X`, the flags do not
carry `PF_EXITING` (0x4, set by the kernel when a task begins to exit), and the start time equals the
one `submit` now records in the pending record (so a reused pid is not mistaken for the runner). Without
`/proc` (macOS) the lock alone decides, as before. With this rule the probe saw the runner dead 0.47 to
0.94 ms after SIGKILL in 30 of 30 kills, against 30 to 59 ms for the lock alone, and never saw a zombie
leader while the rule said live. The lock is still required: the pid alone was the A-01 bug.

**Deterministic reproduction.**
`test_a07_status_is_failed_once_the_runner_leader_is_a_zombie_though_its_lock_is_still_held` starts a
stand-in runner that inherits the flock as `submit` hands it down, starts a second thread, and ends its
leader thread with the raw `exit` syscall (which ends one thread; `exit_group` ends all). The test checks
the condition (state `Z`, `_alive` false, lock held), then reads `status`: on the old code
`{'run_id': 'ef', 'status': 'running'}`; now `failed`, "runner exited without closing the run".
`test_a07_runner_process_liveness_from_proc` covers each `/proc` case with a fake tree.

## 5. What remains unproven

- That GitHub's runner takes the scope path is *derived* (section 2), not observed. The new assertion
  message prints `argv[:4]` and `limits_json`, so the next failure, if any, says which.
- Whether `MemoryMax` is enforced in a `systemd-run --user --scope` on GitHub's runner (a user
  manager with the memory controller delegated) is not known. If it is not, the oom case now fails
  every time with "that limit is not enforced" instead of passing or timing out by chance. That would be
  a finding about the environment, not a flake, and would need its own card.
- How long the scope path takes on GitHub is not measured. Twenty consecutive green `ci` runs after this
  change are the acceptance test for both causes; they have not been run (this session cannot push).
- The zombie-leader window was seen on the pod in 2 of 50 kills; that it is the window GitHub hit is
  *derived* from the failure (state seen as gone, lock held) and the absence of any other holder, not
  observed on GitHub.
