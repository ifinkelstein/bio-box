# K-13 bake-off, 2026-10-30: Parquet `seq_chunks` vs bgzip + faidx, scored by LY-06

Run: `python scripts/k13_bakeoff.py GOLDEN_DIR OUT.json` on the laptop (Apple Silicon, DuckDB 2.0.0, pyarrow 26.0.0, one thread). Raw numbers: `2026-10-30_k13_bakeoff.json`. Unit counts and bytes do not depend on the host; the wall times are the laptop's and are recorded only (LY-06 decides on counts). The pod rerun, for R-08 latency, waits for the image with samtools.

Data: the 21 distinct contigs of the golden set (36.5 Mbp), all in one file per layout, the way a 256 MB–1 GB production shard holds many contigs. Queries (seed 20261030): 500 random 1 kb slices (a gene), 200 random 20 kb slices (a neighbourhood), and the 9 contigs ≥ 1 Mbp whole.

Units are what each layout must read to answer: Parquet row groups scanned (DuckDB profiler, `row_groups_scanned`) and BGZF blocks decompressed (from the `.gzi`). Bytes read are compressed bytes fetched from the file: DuckDB's `total_bytes_read`, including the footer it reads on every query, and for bgzip the blocks themselves. Bytes decoded is an upper bound for Parquet (whole `seq` column chunks of the scanned row groups) and exact for bgzip.

## Findings

1. **The S0 default row-group size was wrong.** With 1,024 chunks of 64 KB per row group, the golden set is one row group, and every 1 kb slice reads the whole file (10.8 MB) and decodes 36 MB. `ROW_GROUP_CHUNKS` is now 16 (1 MiB of sequence per row group), which reads 344 KB and decodes at most 1.9 MB per slice. This is the LY-06 row-group decision for Parquet; it stands whatever K-13 decides.
2. **bgzip reads 13–17× fewer bytes and decodes 23–29× fewer bytes per gene or neighbourhood slice** than the best Parquet layout with an affordable footer (64 KB × 16). Parquet can match bgzip's decoded bytes only with 64 KB row groups, and then the footer is ~430 bytes per row group: 240 KB here and ~20 MB for a 1 GB shard, read on every file open, so its bytes read stay 11–14× higher. Whole-contig reads cost about the same in both formats.
3. **Row groups that straddle two contigs cost one extra row group.** Zone maps are per column, so a row group holding the end of one contig and the start of the next has `raw_digest` min ≠ max and cannot be pruned on `chunk_ix`. That is why Parquet slices average 1.6–2.2 row groups, not 1. Writing row-group boundaries at contig boundaries would remove it (not done).
4. **Statistics on the `seq` column were waste.** pyarrow writes min/max for every string column by default; on 4–64 KB sequence strings this made a 4.8 MB footer (4 KB chunks). The store writer now keeps statistics only on `raw_digest`, `chunk_ix` and `contig_len` (`SEQ_CHUNK_STATS`), which LY-03 requires and which are all that prune.
5. **Storage is a wash**: 0.30 bytes/bp for Parquet at ≥ 1 MiB row groups, 0.31 for bgzip with its indexes, inside the 0.27–0.30 assumed in §2A.4.

## What the rule says, and the decision it needs

`data_layer_and_tests.md` §2A.1 says the format that reads fewer storage units, with bytes decoded, wins, and that if bgzf wins the primary flips to bgzf shards, keeping `raw_digest` and the occurrence tables, recorded as an ADR. By that rule bgzip wins on the gene and neighbourhood classes and ties on whole contigs.

The flip changes the plan's "SQL-native" argument for Parquet: DuckDB cannot read BGZF, so `seq_get` in SQL would need a UDF (Python) or would read a small Parquet mirror. Options for the PI:

- **A. Flip (what the rule says).** bgzip shards are primary; `seq_locator` maps `raw_digest` to (shard, `.fai` name). Python and CLI slice through `.fai`/`.gzi`; samtools, pysam and MMseqs2 read the shards directly with no extract step. SQL slicing goes through a registered Python UDF. Same storage.
- **B. Keep Parquet primary at 64 KB × 16 and accept 13–17× more bytes read per slice** for SQL-native slicing. At the R-08 targets this is likely still fast enough (3.7 ms per slice on the laptop vs 0.1 ms for bgzip), which latency would confirm on the pod but, under LY-06, does not decide.
- **C. Both.** Parquet for SQL and bulk scans, bgzip shards as a slice-optimized mirror (the "optional mirror" of DEPLOYMENT §3.10). About 2× sequence storage: ~1.8 TB at S6 instead of ~0.9 TB, inside the 30 TB scratch.

Until the PI chooses, the code keeps Parquet primary (with the corrected row-group size) and the bgzip writer and reader exist for O-EXTRACT either way.
