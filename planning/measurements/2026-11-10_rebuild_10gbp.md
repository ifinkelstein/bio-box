## Defects (each with how to reproduce)

1. **`partners_of` (card B-31) is 12 times slower than the query it replaced at 10 Gbp and reads
   more.** On `rN.1`, the largest NR50 → NR50 partners: 9.49 s and 556 `tape_tokens` row-group reads
   of a 93-row-group table, against 0.795 s and 99/197 postings row groups for the ladder's query, same
   answer. The anchors sit on 2,399 contigs whose random uids cover every row group, and the lookup's
   cache (32 decoded row groups, `TapeTokenLookup`) is smaller than the table, so row groups are read
   about six times over. On `rN.1b` (26 row groups, fits the cache) it read 26/26, still 5 times slower
   (0.651 s against 0.133 s). Reproduce: `python scripts/stress/build_stage_pod/r10_queries.py
   /tmp/if2453/r10/root rN.1 OUT`, entries `partners_top_nr50` and `partners_prok_top_nr50`. Also:
   the lookup's cache outlives a query, so a second `profile_query` of the same lookup on the same
   connection reports 0 reads; `r10_queries.py` opens a new connection per neighbour query.
2. **Clustering breaks the 300 CPU-minute rule and nothing stops it.** `rN.1.cluster` ran 2,195.91
   CPU-minutes in one process (`over_cpu_budget: true` in `runs/stage=rN.1/cluster.json`); `build-stage`
   gates ingest and scans before they start but not clustering. Known in kind (ladder finding 3, card
   B-24's clustering rewrite), not yet gated.
3. Not settled, an open question rather than a defect: `rN.1.cluster` records a peak RSS of 11,488 MiB
   (`os.wait4`, the largest single process of the step's tree), while the ladder's driver recorded
   46.1 GB for the same clustering with the older code, and the unit's `MemoryPeak` was 45.4 GiB at
   16:06 (cgroup memory includes page cache of the files MMseqs2 writes). Whether the current code's
   MMseqs2 processes are smaller or one of the two measurements misses something was not checked.
4. Cluster membership of one protein reads every `cluster_member` row group (173/173 on `rN.1`): the
   sort key is (level, cluster_uid, member_uid). Card B-27 targets this.

## Runbook errors and unclear places (kept as found)

1. RUNBOOK §2 says a finished build logs `all 13 steps done`. Without `--library` it is
   `all 12 steps done` (`r10-S1-1`): the count is the length of the step list, one more per library.
   §2 also never says that `--library` may be left out; the code allows it (`Build.libraries = ()`).
2. RUNBOOK §2: "For a real Pfam scan by day, with the real profile: `--scan-jobs 10 --scan-cpus 4`."
   That is 40 threads, the account's whole day cap, while the cap is a total across every agent of
   the account (three other agents' test suites run beside a build). The runbook does not say that
   `--scan-jobs` × `--scan-cpus` plus everything else the account runs must stay under the cap.
3. RUNBOOK §2 ("A shard that fails stops new launches. Shards already running finish and publish")
   and §3 (a step running when `STOP` appears "finishes its command. `run-step` then publishes
   nothing") together mean: after `STOP`, every shard that ends while `STOP` is still present is
   discarded, not published. §3's "During a scan in shards it checks before each shard launch,
   launches no more, and waits for the shards that run" reads as if the running shards were kept.
   Removing `STOP` as soon as `build-stage` logs `launching no more shards` keeps all but the first
   (what `r10_phase2.sh` does).
4. RUNBOOK §0 `bio-box()`/`biopy()` put `python -c '...'` one-liners inside nested quotes; run through
   `ssh '...'` and `bash -c "..."` they need a third quoting level, and the first attempt here
   (`r10-check-S1`) failed with `unexpected EOF while looking for matching '"'`. A script file
   (`r10_verify.py`) avoids it.
