# Review of hybrid clustering before the release train of `r26.11.4` (DEC-77 (5), DEC-81 (1))

Prepared 2026-11-26 for the PI's signature, by an agent that read the records, the code and the tests; nothing was
built, tested or run. Pod reads were `df`, `du`, `find`, `date` and one `python3 -I` read of three cut records
(*measured*, `wilkcomp02`, 2026-11-26 13:10 to 13:25 CST). Labels follow AGENTS §6; *inferred* marks what I concluded
from reading code rather than saw run. "265 M proteins" is the design's central *estimate* throughout.

## 1. What is being decided

1. Launching with `CLUSTER_METHOD=hybrid-b1` (the train's default) makes `r26.11.4` the first release whose NR90 is
   the fast k-mer step alone and whose NR50 has two sensitivity steps instead of three. The published release is
   never rewritten (AGENTS §3.10), so its clusters stay as they are.
2. Earlier releases are untouched; their `cluster_uid`s keep their meaning. A `cluster_uid` is a hash of a member set
   and the level's thresholds, not of the method: a cluster with the same members keeps its id across methods.
3. Reversible later in principle: each release clusters from scratch (DEC-24) and the code keeps `cascade` and
   `hybrid-a`. In practice cascade NR90 is refused on this pod at `r26.11.4`'s size (one step of ~25,700 CPU-min,
   *derived*, over the 20,000 cap), so going back needs more compute (card A-28) or a raised cap.
4. The method is written in the plan records (`format: 2`, `"method": "hybrid-b1"`) and as ledger rows with reason
   `method:hybrid-b1`; the tables' `cluster_params_hash` is the same for both methods (`params_hash` has no method).
5. DEC-81 (7): if the train starts in December the release is named `r26.12.1`.

## 2. What changed, in plain words

**The method.** MMseqs2 clusters in two kinds of stage. A *redundancy step* groups proteins by shared k-mers and
confirms each grouping with one alignment (fast, near-linear; misses pairs that share few k-mers). A *cascade step*
runs an all-against-all k-mer prefilter at a set sensitivity `-s`, aligns the candidates and clusters again (slow,
grows faster than linearly; finds the remote pairs). Until now each level ran the redundancy step and then cascade
steps. `hybrid-b1` keeps NR90's redundancy step only and drops NR50's last, most sensitive step:

| Level, step (code's call numbers) | What MMseqs2 does there | Cascade (`r26.11.1` to `.3`) | `hybrid-b1` |
|---|---|---|---|
| NR90 redundancy (`nr90.00`-`09`) | k-mers, then align at >= 90% identity, >= 80% coverage | run | run, the same ten calls |
| NR90 cascade (`nr90.10`-`14`) | prefilter `-s 1`, align, cluster the representatives | run | dropped |
| NR50 redundancy (`nr50.00`-`10`) | the same at 50%, over the NR90 representatives | run | run |
| NR50 step 1 (`nr50.11`-`13`) | prefilter `-s 1`, align, cluster | run | run |
| NR50 step 2 (`nr50.14`-`17`) | prefilter `-s 2` on a shared index, align, cluster | run | run |
| NR50 step 3 (`nr50.18`-`21`) | prefilter `-s 3` on a shared index, align, cluster | run | dropped |
| members, tables | align members to representatives; write `cluster_member` etc. | one `finish` | two level finishes + publish |

DEC-78 settles what "linclust NR90" means: the redundancy step as `mmseqs cluster` runs it inside itself
(`--spaced-kmer-mode 1`, `--alignment-mode 3`, `--comp-bias-corr 0`), not a plain `mmseqs linclust` call. Mode 3
measures identity on the alignment, so the 90% is enforced, not estimated from the score.

**The machinery**, each needed because of size (the design note's four "walls" at 265 M proteins):
- *Plan format 2*: the method is part of the plan, so a release is never reused across methods and a resumed train
  keeps its method. Format-1 plans (the published releases) still read and can be redone (card R-02).
- *Split finish* (`cluster.finish.nr90`, `cluster.finish.nr50`, then `cluster`): one finish would be ~440 CPU-min at
  265 M (*derived*: `r26.11.3`'s 170.01 CPU-min / 102.34 M x 265 M), over the 280 process guard; each half ~220.
- *Scratch pruning* (`clean_consumed`): deletes MMseqs2 intermediates once the step that consumed them is recorded
  and verified, writing the intent to `.pruned.json` first. Unpruned scratch would be ~715 GB (*derived*,
  2,696 B/protein from `r26.11.3`), above the ~450 GiB `/tmp` has.
- *Shared-index `createindex` exempt from the process cap* (DEC-77 (3)): the `-s 2` index over ~63-70 M targets is
  ~480-560 CPU-min in one process (*derived*, card B-68's fit), over 280; it may now run up to the profile's
  `cluster_cpu_min_max` (20,000), the same cap DEC-29 gives the unsplittable prefilter.
- *The watch's cap for a running cut* (`r50_watch.py`, cards A-27, R-05, R-05b): a running cut gets the exempt cap
  only if build-stage's own test grants it (estimate over the part budget, within the cap); otherwise 280.

**The ~97.7%.** At fixed proteins the hybrid NR90 is the cascade's intermediate clustering, which the cascade's later
steps only merge; so each hybrid cluster lies inside one cascade cluster (C-38c: 0 of 15,219,898 joins disagree,
*measured*) and at most (hybrid count - cascade count) cascade clusters split. That gives at least 97.69% of
`r26.11.1`'s cascade NR90 clusters unchanged (*derived*: 1 - 764,370 / 33,117,773) and at least 98.07% of
`r26.11.3`'s (1 - 1,371,310 / 71,208,987). DEC-77 (2)'s wording "of unchanged NR90 clusters" is circular (an unchanged
member set keeps its id by construction, as the audit said). Release to release, growth churns too: `r26.11.2` to
`r26.11.3` (cascade both) kept 96.02% of NR90 member sets and 77.32% of NR50 (*measured*, `c35_check.py`). The
combined share for `r26.11.3` to `r26.11.4` is not measured; the order is 93-95% at NR90 (*estimate*: 0.960 x 0.981,
assuming independence, and `r26.11.4` adds far more proteins than `r26.11.3` did) and lower at NR50.

**How far beyond what was run.** The largest real run of each part of `hybrid-b1`, against 265 M (*derived* ratios):
NR90 calls, 102.34 M inside `r26.11.3`'s cascade (x2.6); finish, 102.34 M (x2.6); the `-s 2` `createindex` fit,
24.3 M targets against ~63-70 M (x2.6-2.9, all five fits at 18 threads); NR50 step 1 as one DEC-29 process at
~95-100 M targets (*estimate*), fitted to 36.2 M (x2.6-2.8); `hybrid-b1`'s NR50 on a linclust NR90, pruning, split
finish and the DEC-77 exemption: fixtures only (hundreds to ~1,000 proteins). Cascade parts ran at 0.69 to 0.92 of
their estimates and the one DEC-29 process at 0.656 in `r26.11.3` (*measured*, release note §3): the laws have so
far erred high.

## 4. What the tests show and do not show

- **Independent oracle (card R-03, `tests/r2/test_r03_hybrid_oracle.py`, 20 tests).** NR50 of `hybrid-b1` equals one
  `mmseqs cluster ... -s 2 --cluster-steps 2` on the build's `rep90`, cluster for cluster and call for call (19
  calls); NR90 of every hybrid mode equals one `mmseqs linclust` with the three flags stated; planted families are
  recovered. Inputs: the S0 fixture, a planted set, a near-threshold set (fixed seeds). Shown able to fail (a
  one-step oracle gives 166 against 163 clusters). Limit: only the call checks tell two NR50 steps from three.
  Run on the pod 2026-11-25: 20 passed in 150.44 s; merged tree with `tests/r0`: 244 passed.
- **Two drivers of the same code (not oracles, AGENTS §5.2).** B-71's byte identity of `run` at 1 and 4 threads and
  `run_split` at 2 parts; B-72's pruning, split finish and stop-and-resume; R-02's 79 tests (12 with MMseqs2) of a
  kill at each point of `clean_consumed`, format-1 redo and the method rows. They prove determinism and that pruning
  and resume change no byte, on fixtures.
- **Driver logic without MMseqs2.** R-05 (13 functions, 55 cases; 37 seen failing first), R-05b, A-27 (13 functions).
- **Where run.** B-71, B-72 and A-27 (merged 08:29, 10:05 and 11:22 on 2026-11-25) have no test run in their rows or
  commits; their files were run again under the audit's cards: targeted 462 passed in 772.09 s (clustering, watch,
  R-02, B-74 files and `tests/r0`, 2026-11-25 23:20-23:35) and `ci` green at `eb46785`, merged as `1783928`. The last
  whole-suite pod run (8 shards, before R-05b) had two failures, one fixed by R-05b, one a CPU-time test that passes
  on a quiet pod (STATUS R1). No pod suite since: the wave builds (W0). GitHub Actions has no MMseqs2, so every
  clustering test above that needs it is skipped there; only the pod has run them.
- **Never run at scale.** `hybrid-b1` has never clustered a real release end to end, at any size. No kill in the
  middle of pruning on real data (fixtures with a patched `rmtree` only). The DEC-77 exemption and the watch's new
  live cap have never met a real cut over 240 CPU-min (`r26.11.3`'s largest was 115.1). **No record of the A-27
  rehearsal** (`release_train.sh rehearse` with `hybrid-b1`, the card's acceptance) was found: no `rh` directory under
  `/tmp/if2453/c46/` and no `dry-run-before.txt` anywhere under `/tmp/if2453` to depth 7 (*measured*, 2026-11-26).
  STATUS line 416 (the Antigravity handoff) names a "hybrid-b1 rehearsal" with no record.
- **Branch `task/R-03` (`5811b41`, 13 tests, unmerged).** They assert that the hybrid NR90 equals plain `mmseqs
  linclust` with the level's thresholds, and fail: plain linclust gave 859 against the build's 857 clusters on the
  fixture and 239 against 240 on a planted set, and joined one planted pair of 85.6% gapless identity at NR90 that the
  build keeps apart. DEC-78 kept the build's flags, so these tests document the difference rather than a defect.

## 5. What the audit found and what was done

- **R-01**: B-71 broke `test_b54_legacy_pre_b54_cut_records_remain_reusable_under_b49` on Actions (`KeyError:
  'method'`) during 27 red `ci` runs nobody read. Repaired; with R-10, `ci` green at `eb46785` (2026-11-26).
- **R-02 (a)**: `clean_consumed` deleted intermediates before recording the prune; a kill between them would have made
  the resume redo the whole NR90. Now the intent is written atomically first and a resume finishes it. Tested
  (fixtures, kill injected at each point).
- **R-02 (b)**: a prune already recorded never removed what a later redo wrote again. Fixed; tested.
- **R-02 (c)**: since B-71 every cut record carried a new field, so a format-1 release (all published ones) could
  not be redone after lost scratch. Format-1 now writes the old record and keeps the old refusal. Tested on a
  format-1 work directory.
- **R-02 (d)**: the method was not in the ledger although DEC-77 (2) said so. Now one row per level with reason
  `method:<mode>` (none for `cascade`, whose ledger stays byte for byte). Tested. `params_hash` unchanged.
- **R-03**: the hybrid modes were tested only against themselves. Now an oracle (§4), which found the DEC-78 point.
- **R-05**: the watch let every running shared-index cut go to 20,000 CPU-min, needed or not. Now only where
  build-stage grants the exemption. Tested. **R-05b**: a format-1 plan's running cut gets no exemption. Tested.
- **DEC-78**: wording only; C-38c's +2.31% ran the code's own calls, so it stands for what the code runs.
- Process (audit §2.2): A-27 was merged at 11:22 and pushed before the PI's "approved" at 11:27 on 2026-11-25;
  B-71, B-72 and A-27 each touched a file outside their card.

## 6. Open points that touch this release

1. **`cluster_uid` and the method (R2 item 1).** Keeping it out lets an unchanged member set keep its id (the
   property users rely on); the cost is that `cluster_params_hash` says nothing about `-s` steps, so the tables alone
   cannot tell `r26.11.4`'s NR50 from a cascade NR50. My reading: low risk, keep, and name the method in the
   announcement; but decide now, since changing it after `r26.11.4` is published rotates every id once more.
2. **One-process `run()` writes no plan record (R2 item 9).** Not reached by `r26.11.4`: a release whose
   one-process estimate is over 240 CPU-min clusters in parts (`r26.11.3`'s was 37,779). Affects tiny releases only.
3. **`train_est.py --cluster-method` defaults to `hybrid-b1`, the library to `cascade` (R2 item 8).**
   `release_train.sh` always passes the method (line 732), so low risk; a hand run of `train_est.py before` without
   the flag would price a hybrid clustering.
4. **Threads (STATUS W1).** The train does not use 80 threads for clustering: `Q=40` makes its unit's CPU quota 40,
   and parts run `J=2` at a time with `CPUS=18` threads, one-process steps at `T=18` (`release_train.sh` lines 50-53,
   755; `stage.py` 2552). `r26.11.3` ran with exactly these (`--threads 18 --scan-jobs 2 --scan-cpus 18`), and the
   clustering fits are from 18-thread processes, so the fits match how the train runs. Guards: parts are cut at 240
   estimated against the 280 process guard (17% headroom; `r26.11.3` parts used 0.69-0.92); each finish half ~220
   (27%; 12% at 300 M), with no exemption if it passes 280 (the train stops and needs a code change); the DEC-29 and
   DEC-77 one-process steps are watched only at 20,000, so an overrun there costs CPU but stops nothing until the rate
   guard reads its record afterwards. Consequence: the wall is ~15-19 h, not 8-10 h (*derived*: 36,570 / 36-40 CPUs;
   the design's own 40-core column says 15.2 h ideal, ~19 h effective). Raising `J`/`Q` to reach 80 threads would put
   the train where W1 saw Pfam shards pass 280 (about 7% more CPU per shard at 56 threads than at <= 40, and over
   1.19 of the estimate, unfinished, at 80; *measured*, STATUS W1, W3): do not.
5. **`/tmp` across the whole train, not only scratch.** Free now 426 GiB (*measured*, `df -B1G`, 13:20); the 18
   stages still to build add perhaps 100 GB (*estimate*: `l0seq`+`l1` hold 86 GiB for the 13 stages' 119.9 Gbp and
   part of `V2`; 167 Gbp are to come). The train then needs
   230-280 GB of scratch above `TMP_MIN_GB=100` (330-380 GB free, *estimate*), writes ~113 GB of release files
   (*derived*: `r26.11.3`'s 43.7 GB x 2.59), and builds a pack of ~210-230 GB (*derived*: 89.0 GB x 2.39-2.59) on the
   same disk, where the packs of `r26.11.2` (34 GiB) and `r26.11.3` (83 GiB) already sit (*measured*, `du`). The pack
   build has no free-space guard (`release_train.sh` 824-835 run it outside `r50_watch.py`; *inferred*), so a shortage
   there is `ENOSPC`, not a clean stop. The budget is not closed: it may need `r26.11.2` retired under DEC-66 first
   (a PI decision) or the pack placed elsewhere.
6. **RUNBOOK's launch example would stop this release (*inferred*).** "Cutting the next release" launches `run
   --parts 24`. A forced count removes the part budget, so neither DEC-29 nor DEC-77 applies: NR50 step 1's 24 parts
   would each rebuild a k-mer table of ~95 M targets (~330 CPU-min each, *derived*: 240 at 68.3 M targets, linear)
   and the one-process `createindex` would be
   killed at 280. `r26.11.3` ran without `--parts`. Launch without it.
7. **The dry run does not show the hybrid cost or the method.** Its "Clustering:" line is the cascade law
   (`stage.cluster_cpu_min`, ~120,000 CPU-min at 265 M), and `format_plan` prints no method, though RUNBOOK says it
   does. The hybrid estimate appears only in `$WORK/estimate/before.json`, written when `run` starts.
8. **NR50 sensitivity loss grows**: +1.40%, +1.43%, +1.71% more clusters without step 3 from `r26.11.1` to
   `r26.11.3` (§3). C-38c showed NR50 loss concentrates on 50-70% identity partners (§3 of that note).

## 7. What a dry run and a rehearsal would add, and how to run them when the wave has ended

Neither was run: `V2` and 18 stages are still to build, the train refuses while a build unit is active, and the plan
needs every stage complete. Use a fresh mirror of `plan/task-cards` as `$TREE` and a fresh `WORK`, as `r26.11.3` did.

**Dry run** (RUNBOOK; read-only, seconds):
```
ROOT=/tmp/if2453/r10/root WORK=/tmp/if2453/c46/train_r26_11_4 TREE="$TREE" \
  bash "$TREE/scripts/stress/build_stage_pod/release_train.sh" --dry-run
```
Go: `Next release: r26.11.4` (or `r26.12.1` in December); 32 stages (the 13 of `r26.11.3` in order, then the 19);
`Excluded stages: none`; a cut with `part_cpu_min` 240.0 and `one_process_cpu_min_max` 20000.0 and no `parts`;
`Action:` a first launch. Stop: any stage excluded, `refused`, `resume`, or `parts` in the cut. Then `df -B1G /tmp`
against §6.5's budget.

**Rehearsal** (A-27's acceptance; small units of <= 4 threads and 8 GB; needs a quiet pod):
```
WORK=/tmp/if2453/c46/rh_hybrid TREE="$TREE" CLUSTER_METHOD=hybrid-b1 \
  bash "$TREE/scripts/stress/build_stage_pod/release_train.sh" rehearse
```
Go: exit 0, the line `rehearsal: OK (...)` and `$WORK/rh/OK`; then, in `$WORK/rh/root`, `r26.11.2`'s
`l2/cluster_plan/.../cluster.plan.json` holds `"format": 2, "method": "hybrid-b1"` and its clustering ledger has the
`method:hybrid-b1` rows. Stop: any `FAILED:` in `$WORK/driver.log`. What it proves: the driver cuts a hybrid release
after a cascade one, verifies, packs and reuses. What it cannot: it forces `--parts 2` on three small genomes, so it
never meets DEC-29, DEC-77, pruning at size or the space guards. Only `r26.11.4` itself reaches those; the first hours
of the real run are the test (watch `estimate/before.json`, the first `.cut` records and `scratch_peak`).

## 8. Recommendation

**Launch with named conditions**, for three reasons. (1) The code does what DEC-77 and DEC-78 say; each audit defect
is fixed and tested; the method's NR50 equals a standard MMseqs2 command and its NR90 calls have run at 102 M inside
every cascade release. (2) The cascade cannot cluster `r26.11.4` on this pod at all, so the alternative is waiting,
not the old method. (3) What is untried at scale (pruning, split finish, the exemption, the space budget) is
guarded, resumable, and cheap to watch in the first hours, provided the launch avoids the two traps in §6.5 and §6.6.

For the PI to sign (yes / no):
1. `hybrid-b1` for `r26.11.4`, accepting ~1.4-1.7% more NR50 clusters and ~1.9-2.3% more NR90 clusters.
2. `cluster_uid` stays without the method (R2 item 1), the method named in the plan, the ledger and the announcement.
3. NR50 step 1 as one DEC-29 process (~4,000 CPU-min, *derived*) and the `-s 2` `createindex` under DEC-77 (~480-560),
   both under the 20,000 cap.
4. The rehearsal of §7 is run and passes before the launch, and its output is kept with the release note.
5. Launch without `--parts`, from a fresh `WORK`, with the train's thread defaults (`T=18 J=2 CPUS=18 Q=40`); no
   80-thread setting for clustering. Planned wall ~15-19 h of clustering.
6. Launch only when the dry run shows §7's go lines and `df` shows the space of §6.5; if short, retiring `r26.11.2`
   is put to you as its own decision first.
7. RUNBOOK's `--parts 24` example and its sentence on what the dry run prints are corrected by a card (not before
   the launch is needed).
